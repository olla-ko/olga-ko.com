# Внедрение автотестов и TDD в olga-ko.com

Дата: 2026-07-25
Статус: согласовано, готово к планированию реализации

## Зачем

Ревью админки нашло пять реальных дефектов подряд: потеря правок при одновременном
сохранении, потеря истории при удалении версии, запись в произвольную ветку,
призрачная версия в ленте и ложный бейдж «не опубликовано». Все пять сидели
в **чистой логике принятия решений**, вплетённой в Express-обработчики.

Показательная деталь: чтобы проверить исправление конфликта сохранения, логику
пришлось вручную переписать отдельным скриптом — вызвать её из `admin/server.js`
невозможно. Это и есть основной сигнал: логика не отделена от транспорта.

Цель — сделать эту логику проверяемой автоматически и закрепить привычку
«баг → сначала тест, потом починка».

## Границы

Сайт (вёрстка, стили, содержимое страниц) не меняется. Рефакторинг —
перекладывание кода без изменения поведения.

## Архитектура: функциональное ядро, императивная оболочка

Из [`admin/server.js`](../../../admin/server.js) (571 строка) выделяются модули
чистых решений. `server.js` остаётся оболочкой: HTTP-роутинг, авторизация,
обращения к GitHub API.

**Жёсткое правило для новых модулей: ноль зависимостей.** Ни Octokit, ни Express,
ни файловой системы — только данные на входе и решение на выходе. Тест такого
модуля не требует моков.

### `admin/lib/save.js`

```js
// Допустима ли ветка записи (защита от записи в произвольную ветку).
isValidTarget(target) -> boolean            // только "main" | "drafts"

// Решение о сохранении (оптимистичная блокировка).
saveDecision({ target, clientSha, currentSha, mainSha })
  -> "ok" | "conflict" | "need-main-sha"
```

Правило конфликта: конфликт есть, если файл на целевой ветке изменился с момента
загрузки клиентом (`currentSha !== clientSha`). Исключение — черновик «от
опубликованного»: клиент основан на актуальном `main` (`mainSha === clientSha`),
на `drafts` лежит устаревшая копия, её законно перезаписать.

Третье состояние `need-main-sha` существует ради производительности: чтение
ветки `main` — лишний запрос к GitHub, и делать его при каждом сохранении
черновика недопустимо (сохранение — самое частое действие в редакторе). Функция
остаётся чистой, а оболочка дочитывает недостающие данные только по запросу
и спрашивает решение повторно. Контракт `mainSha`: `undefined` — ещё не читали;
`null` — читали, файла на `main` нет; строка — sha.

### `admin/lib/versions.js`

```js
// Лента версий: какие коммиты показывать и с каким статусом.
// aheadShas — коммиты, реально ушедшие вперёд в drafts; truncated — признак
// усечённого ответа compare (см. ниже).
buildVersionList({ mainCommits, draftCommits, aheadShas, truncated }) -> Version[]

// Схлопывание подряд идущих версий с одинаковым содержимым файла.
// blobShas — массив той же длины и порядка, что versions.
dedupeVersions(versions, blobShas) -> Version[]

// Можно ли удалить версию: набор гардов.
// targetCommit — удаляемый коммит, kept — коммиты новее него.
checkDeletable({ compareStatus, targetCommit, kept, commitFiles, path })
  -> null | { error }

// План пересборки ветки без удаляемого коммита (без выполнения).
planVersionDeletion({ kept, blobs }) -> Step[]
```

`Version`: `{ sha, date, message, published, isCurrent, viaAdmin }`.

Учитывается усечение ответа `compare` (GitHub отдаёт максимум 250 коммитов /
300 файлов): при усечении классификация деградирует консервативно — лучше
показать лишнюю версию, чем скрыть настоящий черновик.

### `admin/lib/drafts.js`

```js
// Бейдж «не опубликовано» по файлам каталога.
computeHasDraft({ paths, mainTree, draftTree, changedAheadInDrafts, truncated })
  -> Map<path, boolean>
```

Черновик есть, если содержимое на `drafts` отличается от `main` **и** файл реально
изменён в `drafts` впереди `main`. Одной разницы недостаточно: если файл правили
напрямую в `main`, ветка `drafts` просто отстаёт — это не черновик.

## Инструмент

Встроенный `node --test` (Node 24 уже используется проектом) — **ни одной новой
зависимости**. В корне проекта сейчас всего четыре пакета; тянуть Jest или Vitest
ради проверки чистых функций несоразмерно.

```
test/            тесты bake.js и инвариантов сборки
admin/test/      тесты save.js, versions.js, drafts.js
```

Запуск: `npm test` в корне (`node --test test/ admin/test/`).

## Тесты контента и сборки

Сверка целых страниц с эталонными файлами не используется: такие тесты ломаются
от любой правки CSS-класса и быстро начинают раздражать. Вместо этого:

**`bake.js` на фикстурах.** Маленькие эталонные md в `test/fixtures/`, проверяется
структура результата:
- карточка портфолио собирается со всеми полями, `<<Теги>>` разбираются;
- запись резюме собирается из `<<Период>>`, `<<Должность>>`, `<<Компания>>`;
- картинка с ручным размером `![](x.png =705)` даёт `width="705"`;
- картинка без размера ширины не получает;
- заголовкам проставляются `id`.

**Инварианты собранного сайта.** После сборки проверяется: ожидаемые страницы
существуют и непусты; в корне лежит редирект на `/portfolio-ru/`; `/home.html`
существует; у md-страниц есть ссылка возврата.

## Гейт в CI

Правки кода блокируются красными тестами; публикация контента — никогда.
Реализация без сторонних действий: в [`.github/workflows/pages.yml`](../../../.github/workflows/pages.yml)
добавляется job `test`, а `deploy` получает `needs: test`.

Job `test` определяет список изменённых файлов и пропускает прогон, если **все**
они подходят под контент — то есть под то, что пишет админка:

```
^content/[^/]+\.md$      портфолио и резюме
/content\.md$            страницы и md-копии кейсов
```

Если список изменённых файлов определить нельзя (ручной запуск `workflow_dispatch`,
первый пуш, force-push — `github.event.before` пустой или нулевой), тесты
**запускаются**: безопасный вариант по умолчанию.

Существующая проверка ссылок (`scripts/check_links.py`) остаётся в job `deploy`
без изменений.

## Процесс

Тесты на уже написанный код — *характеризующие*: они фиксируют текущее поведение,
а не проверяют его правильность. Настоящий цикл TDD начинается с нового кода,
и главное правило одно:

> **Найден баг → сначала тест, воспроизводящий его (красный) → затем починка (зелёный).**

Каждый из пяти найденных ревью дефектов становится таким тестом-регрессией.
Правило фиксируется в `README.md` (документ для разработчика).
`РУКОВОДСТВО.md` не трогается — оно написано для не-программиста.

## Этапы

| Этап | Содержание | Обоснование порядка |
|---|---|---|
| 1 | `npm test`, структура каталогов, модуль `save.js` с тестами и регрессиями на конфликт сохранения, включение гейта в CI | Малый объём, проверяет подход на практике, дисциплина начинает действовать сразу |
| 2 | Модули `versions.js` и `drafts.js` с тестами, включая регрессии на призрачную версию и ложный бейдж | Самая сложная логика, наибольшая концентрация дефектов |
| 3 | Тесты `bake.js` на фикстурах и инварианты сборки | Защита содержимого сайта |
| 4 | Правило «баг → тест» в `README.md` | Закрепление привычки |

Каждый этап заканчивается зелёным прогоном `npm test` и неизменившимся выводом
сборки (`_site` побайтово совпадает с состоянием до этапа).

## Вне объёма

- **Тесты интерфейса админки** (`admin/src/app.tsx`, 748 строк). Требуют jsdom и
  библиотеку тестирования; админкой пользуется один человек и проверяет глазами.
- **Тесты `scripts/check_links.py`** — 51 строка, сам по себе является проверкой.
- **Покрытие как целевая метрика** — провоцирует писать тесты ради процента.
- **Сквозные браузерные тесты** — ручная проверка превью закрывает эту потребность.

## Критерии готовности

1. `npm test` проходит локально и в CI.
2. Каждый из пяти известных дефектов покрыт тестом, который краснеет при откате
   соответствующего исправления.
3. Коммит, меняющий только контент, деплоится без прогона тестов.
4. Коммит, ломающий логику админки, останавливает деплой.
5. Вывод сборки не изменился: `_site` совпадает с состоянием до рефакторинга.
